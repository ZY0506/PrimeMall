### 4.2 熔断机制（Circuit Breaker）

#### 关于 vendor 目录

本项目的 `vendor` 目录已被删除并加入 `.gitignore`，**不会上传到 GitHub**。
因此代码中所有 `vendor/...` 开头的路径引用（如下文所示）仅供**本地参考**，
实际编译时 Go 会从 `go mod download` 下载的模块缓存中读取源码。

> 💡 **什么是 vendor**？  
> `vendor` 是 Go 项目的依赖本地缓存，把第三方包的源码复制到项目目录中。
> 它的用途是离线编译和版本锁定。但本项目不依赖它，使用 Go Modules 标准模式，
> 构建时自动下载依赖，不需要 `vendor`。

熔断器的代码位于 go-zero 框架的 `rest/handler/breakerhandler.go` 中（通过 `go mod` 管理，
不在本仓库内）。以下内容基于 go-zero v1.10.1 的源代码分析。

#### 状态：✅ 启用（go-zero 原版逻辑，未修改）

```go
// go-zero 官方实现（通过 go mod 管理，不在本仓库）
// 路径参考: github.com/zeromicro/go-zero/rest/handler/breakerhandler.go
func BreakerHandler(method, path string, metrics *stat.Metrics) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            // 实际调用了 go-zero 的 Google SRE 熔断算法
            // 当错误率超过阈值时，直接返回 503 Service Unavailable
            breaker.DoWithAcceptable(...)
        })
    }
}
```

> ⚠️ **注意**：在压测调优阶段，我们曾绕过熔断器（在 vendor 中修改源码），
> 但该修改仅在本地生效，**已随 vendor 删除而还原**。
> 当前版本即为 go-zero 官方原版的熔断逻辑。

#### 原始算法（go-zero Google SRE Breaker）

```go
// go-zero 官方实现（通过 go mod 管理，不在本仓库）
// 路径参考: github.com/zeromicro/go-zero/core/breaker/googlebreaker.go
const (
    window            = time.Second * 10   // 统计窗口：10秒
    buckets           = 40                 // 桶数量：40（每个桶250ms）
    k                 = 1.5                // 熔断强度系数
    minK              = 1.1                // 最小K值
    protection        = 5                  // 保护阈值（前5个请求不熔断）
)
```

**熔断判定逻辑**：
```
接受率 = K × 历史成功请求数
丢弃率 = (总请求 - 保护阈值 - 接受率) / (总请求 + 1)
如果 丢弃率 > 0 且 距离上次强制通过 > 1秒 → 按概率丢弃请求
```

**熔断影响**：在突发高流量导致错误率上升时，熔断器会主动拒绝部分请求（返回 503），
保护后端服务不被压垮。这是生产环境的必要机制，但会表现为"请求失败"。



### 4.3 自适应负载 Shedding

#### 状态：✅ 默认启用

```go
// go-zero 官方实现（通过 go mod 管理，不在本仓库）
// 路径参考: github.com/zeromicro/go-zero/core/load/adaptiveshedder.go
const (
    defaultBuckets       = 50               // 桶数量
    defaultWindow        = time.Second * 5  // 统计窗口：5秒
    defaultCpuThreshold  = 900              // CPU阈值：900m（90%）
    defaultMinRt         = 1000ms           // 最小响应时间
    flyingBeta           = 0.9              // 飞行请求滑动平均系数
    coolOffDuration      = time.Second      // 冷却时长：1秒
)
```

**Shedding 判定逻辑**：
```
1. 检查 CPU 是否超过阈值（90%）
2. 检查当前飞行请求数是否超过历史平均
3. 两者都超时 → 返回 ErrServiceOverloaded（503）
4. 客户端收到 503 后可自行重试或降级
```

### 4.4 熔断 vs. Shedding 的区别

| 机制 | 触发条件 | 效果 | 状态 |
|------|---------|------|------|
| **熔断** | 错误率上升（Google SRE算法） | 直接拒绝请求 | 🚫 禁用 |
| **Shedding** | CPU超90% + 飞行请求超标 | 返回503，客户端重试 | ✅ 启用 |

## 六、Nginx 负载均衡

```nginx
# deployments/nginx/shop.nginx.conf
upstream shop_backend {
    keepalive 64;                                      # 长连接池：64个
    server host.docker.internal:9091 max_fails=5 fail_timeout=60s;
    server host.docker.internal:9092 max_fails=5 fail_timeout=60s;
    server host.docker.internal:9093 max_fails=5 fail_timeout=60s;
}

server {
    listen 8080;
    
    # 长连接
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    
    # 超时
    proxy_connect_timeout 10s;     # 连接后端超时
    proxy_send_timeout 30s;        # 发送请求超时
    proxy_read_timeout 60s;        # 读取响应超时
    
    # 缓冲
    proxy_buffering on;
    proxy_buffer_size 8k;
    proxy_buffers 16 8k;
    
    # 后端重试
    proxy_next_upstream error timeout http_502 http_503;
    proxy_next_upstream_timeout 10s;
    proxy_next_upstream_tries 3;
}
```

> **注意**：压测时 k6 直连 `127.0.0.1:9091`（绕过 Nginx），因为 Windows Docker 下  
> `host.docker.internal` 在高并发时 DNS 不稳定。生产环境下（Nginx与应用同机）无此问题。

### 7.3 预下单 RPC 并行化

```go
// apps/service/order/rpc/internal/logic/order/preorderlogic.go
var wg sync.WaitGroup
wg.Add(3)

// 三个独立RPC同时执行：
go l.svcCtx.UserRpc.CheckUserStatus(...)     // 查用户状态
go l.svcCtx.UserRpc.GetAddressById(...)      // 查地址
go l.svcCtx.ProductRpc.GetSkuListByIds(...)  // 查商品

wg.Wait()  // 等待全部完成
```

> **优化效果**：串行4个RPC（约4×500ms=2000ms）→ 并行3个RPC（约500ms最慢），端到端延迟降低约75%。
